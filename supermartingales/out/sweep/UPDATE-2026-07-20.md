## Findings

1. **No bound moved** — the re-verify-don't-assume instruction on the
   Mehrotra fix is discharged, with the negative result carried as a
   likelihood statement: 57,138 checks positioned to catch any drift
   in either checker's verdict on sweep-era bytes found none, and the
   synthesis-side grep shows the fixed code was never in any sweep
   row's load path to begin with.

2. **The named new lanes do not ride this checking path — stated
   plainly rather than forced in.** E5's batch-CSR lanes
   (the ground tier's CSR path, `EXACT_LQQ_MAX_ENTRIES = 24`)
   verify PFarkas/PSyzygy Phase-V instances extracted from the
   ground-tier BL-cert pipeline; the enclosure-kernel family
   (`maitria-coalition/kernels`, currently the `sweep` family with
   AVX2/NEON lanes) is float-lane, zero-dep, and explicitly
   not-a-TCB. This campaign's checking is fastcheck's exact-$\mathbb{Q}$
   BernCone kernel over bernfmt bytes — its entire dependency
   surface is `bernfmt` + the `num-*` crates (Cargo.toml witness).
   Wiring either new lane in would mean building a new extraction
   path or putting float lanes inside a Trusted tier: forcing it.
   What DID move this path since the sweep is the **streaming-load
   streaming-load shared-structure model** in bernfmt
   (`c3c9a5fe0` + `b5232b995`, Arc tree edges): parse time on a
   representative persist2d cert fell 2.74ms → 0.51ms while check
   time stayed flat — which is exactly why the wins concentrate on
   parse-heavy many-file rows (cliff 1.81×, repulse100_2d 1.36×,
   gaussian twin 1.20×) and vanish where checking dominates.

3. **Where the new stack does not dominate, named per the Pareto
   principle:** the uniform persist_2d twin measured 0.98× (old
   133.6s vs new 135.9s min-wall) — ranges overlap (old
   [138.7, 133.6] vs new [135.9, 141.0]), so the honest reading is
   "statistically indistinguishable", not "regression"; mechanism:
   that row is ~28ms/file of pure BernCone arithmetic on the
   uniform twin's giant exact denominators (the receipts'
   `min_tau_overall` is a $\approx$3,100-digit-over-3,100-digit
   fraction, $\approx$10k bits a side), untouched by the load-path
   change. Corroborating same-instrument baselines from the sweep
   night itself: the persist2d legs' own `fastcheck.json` records
   2m26s (uniform, 4800 files) and 4.7s (gaussian, 19200) — tonight's
   old-binary walls (133.6s / 4.85s) sit right beside them.
   The gaussian twin checks ~100× faster per file than the uniform
   twin (0.25ms vs 28ms) — its dyadic `scale_bits` route pays off
   at check time, not just at synthesis: worth knowing for any
   future 2D lattice leg. RSS on the 19,200-file batch: 4.36MB →
   3.83MB (the streaming-load claim, visible if small at these
   cert sizes).

4. **The cross-paper story is unchanged and now timing-current**:
   their per-row learn+verify runs 5.8–254.5s on an A40 GPU + Z3;
   re-checking the corresponding house certificates from cold takes
   1.4ms–4s per row on workstation CPU under the current stack — except
   the uniform persist_2d twin (136s), whose cost is the price of
   exact rational arithmetic on that twin's denominators, and which
   the gaussian twin shows is a representation choice, not a
   necessity of the row.
